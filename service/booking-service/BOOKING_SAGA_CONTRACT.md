# Creación de reservas: contrato de integración

`POST /api/v1/bookings` requiere `screeningId`, `customerId` y `totalAmount > 0`. Una reserva ocupa un asiento. Booking consulta `GET /api/v1/screenings/{id}` en Movie, guarda PENDING, reserva el asiento, guarda CONFIRMED y devuelve 201 con `Location`. Si la función no puede verificarse o no tiene asientos, devuelve 422 sin crear la reserva.

Booking llama a `PATCH /api/v1/screenings/{id}/reserve` y `PATCH /api/v1/screenings/{id}/release` con el header `X-Booking-Id: <UUID>`. Movie acepta el header opcionalmente para conservar a los consumidores existentes. Para las llamadas de Booking, `bookingId` identifica una única reserva de asiento: repetir `reserve` no vuelve a descontar; repetir `release` no vuelve a sumar. Si `release` llega antes que un `reserve` retrasado, Movie guarda una marca de liberación e impide el descuento tardío. La tabla `seat_reservations` se crea con la migración V5 de Movie.

Booking usa `RestClient` con `@LoadBalanced` para las llamadas a Movie. El nombre lógico `movie-service` se resuelve mediante `SimpleDiscoveryClient`: `MOVIE_SERVICE_INSTANCE_URL` indica la instancia, con valores predeterminados `http://localhost:51100` en local y `http://movie-service:51100` en Docker. El prefijo HTTP permanece en `http://movie-service/api/v1`; no se requiere Eureka. `@Retry` se aplica únicamente a `reserve`: tres intentos totales, 500 ms entre intentos y solo ante `MovieServiceException` (fallos transitorios). Un error HTTP 4xx de Movie se traduce a `ScreeningUnavailableException` y no se reintenta. El retry propio de Spring Cloud LoadBalancer queda desactivado para evitar intentos adicionales.

Cada transición local se persiste en su propia transacción. Si falla la reserva o confirmación, la Saga intenta liberar el asiento y guardar CANCELLED. Si PostgreSQL está indisponible durante la compensación, no se puede garantizar la eliminación inmediata de PENDING. Un proceso periódico busca reservas PENDING antiguas cuando la base vuelve, las cancela y solicita a Movie liberar el asiento con el mismo `bookingId`. Por defecto se ejecuta cada minuto y espera diez minutos de antigüedad para no interferir con solicitudes en curso. Las variables `BOOKING_RECOVERY_INITIAL_DELAY_MS`, `BOOKING_RECOVERY_INTERVAL_MS` y `BOOKING_RECOVERY_STALE_AFTER_MS` permiten ajustar esos tiempos. La liberación remota fallida se registra, pero todavía requiere seguimiento operativo porque no existe una cola duradera para reintentarla.

`GET /api/v1/bookings/{id}` consulta únicamente el snapshot local y devuelve 404 si no existe. `GET /api/v1/bookings` lista las reservas locales. `PATCH /api/v1/bookings/{id}/cancel` acepta reservas confirmadas: guarda CANCELLED antes de solicitar `release` a Movie. Si la liberación falla, registra el error y responde con la reserva CANCELLED; el cambio local no se revierte. Una reserva inexistente devuelve 404 y una reserva pendiente o ya cancelada devuelve 422.
